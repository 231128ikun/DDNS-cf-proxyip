# IP 库管理前端设计与实施说明

- 状态：**待实施的前端设计**；不是已上线功能说明。
- 日期：2026-11-03。
- 设计基线：`beta`，`1353708`；实施前读取最新 `AGENTS.md` 并核对分支更新。
- 适用范围：现有 DDNS Pro 的 IP 库管理功能块。
- 后端基础：池快照、变更计划、只读预览和可选写入回执已通过 PR #16 合入 `beta`。
- 实施对象：Codex 或其他代码实施者。本文给出可执行的行为契约，不授权顺便合并 `main`、部署或调用真实维护／删除接口。

## 1. 目标和边界

### 1.1 要解决的问题

当前同一个输入框承担了导入地址、显示库内容、展示清洗结果和指定删除范围，容易造成以下误解：

1. 不清楚输入框内容是草稿、本次检测结果，还是已保存数据。
2. “入库”名称容易被理解为追加，但现有 `ApiClient.savePool` 默认是 `replace`。
3. 检测完成后可用、未知和无效内容混在输入框中，难以确定实际写入范围。
4. “清空输入”和“删除库内地址”的作用范围不同，却靠同一个文本框表达。
5. 写入后立即 GET 可能读到 KV 的旧值，导致已确认的操作看起来没有生效。

设计目标是让**查询、检测、预览和写入各有明确对象**，而不是增加一套管理后台或更换视觉风格。

### 1.2 本次实施范围

- 在现有 IP 库区域内组织“导入与检测”“管理当前池”“垃圾桶”三种逻辑模式；正常池只显示前两个切换入口，垃圾桶由现有池选择器进入，避免重复入口。
- 分离草稿、检测结果、池读取快照和变更预览的状态。
- 使用已经存在的预览／保存／恢复／洗库 API。
- 明确追加、覆盖、删除和清空的语义。
- 接入可选写入回执，处理旧请求、陈旧读取和失败重试。
- 收敛当前组件和样式，删除被替换的旧实现。

### 1.3 不在范围内

- 不改探针判定、复检策略、DNS 维护规则和垃圾桶写入政策。
- 不新增 KV key、池数据格式、检测历史字段或第二套 API。
- 不改变可选密码、鉴权入口、部署方式或定时任务设置。
- 不把域名池绑定重新搬回运行面板；保留当前配置中心中的绑定入口。
- 不把配置开关搬到全站顶部，不把紧凑域名选择换回大摘要卡。
- 不新建另一套前端入口或页面路由；仍使用 `app/web/` 和现有 `App`。
- 不引入 Redux、重型表格框架、运行时校验框架或新的 UI 组件库。
- 不宣称 KV 支持事务、CAS、全局锁或立即一致的读取。

## 2. 页面组织

外层布局保持现状：导航、解析实况、IP 库区域和工作台的位置不变。只在 IP 库卡片内部调整操作组织。

```text
现有解析实况：保留紧凑域名选择、记录操作和刷新

IP 库管理                           工作台
[当前池选择 ▼] [池操作]              统一检测、写入、维护日志
[导入与检测] [管理当前池]            保留现有进度与维护入口
选择垃圾桶后改为恢复／清理视图

当前模式对应的内容与操作
```

三种模式是**同一组件内的逻辑状态**，不是三个独立产品，也不要求三个常驻页签。正常池显示两个切换入口，垃圾桶复用池选择器进入；不要同时增加另一个同义垃圾桶页签。

| 模式 | 处理对象 | 主要操作 |
| --- | --- | --- |
| 导入与检测 | 待加入的数据和本次检测结果 | 粘贴、远程导入、检测、停止／续检、预览追加 |
| 管理当前池 | 服务端保存的数据 | 读取、视图筛选、选择、导出、预览删除、完整编辑、洗库 |
| 垃圾桶 | 已归档条目 | 读取、选择、恢复、清空垃圾桶 |

### 2.1 池选择

- 保持唯一的当前池 key，不为三个模式另建三套池 ID。
- 复用 `state/pool-options.ts`，保留服务端池顺序和显示名称。
- 选择垃圾桶时进入垃圾桶模式；从下拉框选正常池时使用用户明确选择的 key。若提供“返回上次正常池”动作，才恢复最近正常池；该池已删除时回退默认池并提示。
- 不根据列表数组下标识别池或维护目标。
- 切池取消旧读取，使旧预览失效，清空当前管理视图的选择集。
- 通用导入草稿可以保留，但若草稿来自另一个池，必须显示“来源池”和“目标池”，不能无提示地改写目标。
- 从当前池读取的数据进入池快照，不自动覆盖导入草稿；提供明确的“拷贝到导入区”动作。

## 3. 状态归属

至少区分以下逻辑状态。可以合并到少量 hook 中实现，但不能用同一个 `ipText` 作为所有状态的唯一真相。

| 状态 | 内容与来源 | 谁能修改 | 何时失效 |
| --- | --- | --- | --- |
| 导入草稿 | 原始文本、来源、草稿 revision | 用户编辑、明确导入／拷贝／清空 | 编辑后使派生结果失效 |
| 本次检测 | 源文本快照、结果、进度、中断信息 | 现有批量检测生命周期 | 输入更换、重新检测、放弃任务 |
| 当前池读取快照 | poolKey、完整文本、解析条目、读取状态 | 对应池的服务端读取 | 切池、显式刷新 |
| 完整编辑草稿 | basePoolKey、读取原文、编辑文本 | 用户明确进入编辑并修改 | 切池需确认未提交编辑 |
| 变更预览 | poolKey、mode、提交文本、draftRevision、服务端预览 | 预览请求结果 | 草稿、目标池、mode 或候选集合变化 |
| 写入确认 | 请求所属池、回执、确认后的内容和数量 | 成功提交响应 | 显式采用另一份读取结果或下一次确认写入 |

实现要点：

- 不把读取快照当作“刚写入的数据”，也不把写入回执称为“全球最新数据”。
- 对读取、预览、检测使用 AbortController 和请求序号，复用现有异步保护机制。
- 回调必须核对提交时捕获的 poolKey 和 revision，不能读取回调执行时可能已变化的目标。
- 数据状态变化不得触发无界刷新、重复检测或重复写入。
- 不新增永久状态存储。若以后需要跨刷新恢复草稿，另行设计；本轮不往 URL 或浏览器存储放密钥。

## 4. 导入与检测流程

### 4.1 输入

- 接受现有 IPv4、IPv6、域名、带端口地址、旧元数据和备注格式。
- IPv6 带端口仍用 `[IPv6]:port`。
- 远程导入复用 `ApiClient.remoteLoad`，组件不直接 fetch 第三方 URL。
- 有未提交草稿时，新的远程加载或拷贝必须明确说明会替换草稿；失败不丢原草稿。
- 可提供“规范化／去重”动作，但必须复用现有纯函数，不在组件里再写地址解析或元数据合并。
- 无法识别的内容要显示并让用户修正，不能先静默删掉，再把剩余内容当作完整数据提交。

### 4.2 检测

复用 `state/use-batch-check.ts`、`api/batch-check.ts` 和 `state/batch-resume.ts`，不再写第二套批量调度。

必须保留：

- 每地址请求、手动批量并发配置、主／备用复检。
- 停止、继续和放弃任务。
- 原始源行下标、`sourceIndex`、`sourceComplete` 和结果组。
- 一个源行可能产生多个结果时的进度与最终合并。
- 主动取消不计为超时失败。

需要改变的前端行为：

- 完成检测后保存结果报告，**不自动用结果覆盖原始草稿**。
- 原始源文本仍用于续检和错误定位。
- 可用结果的标准 `line` 用于派生入库候选；失效、未知、无效和未完成内容保留在各自状态中。
- 检测中暂不提交会变动的候选集合。按钮禁用时显示“检测中，请等待或先停止”等明确原因。
- 不给手动批量检测无条件传 `concurrency: 'all'`。手动检测仍按配置；解析实况既有全并发策略保持原状。

### 4.3 结果视图

默认展示可用结果；其他分类必须有可见数量和入口，不能静默丢弃。

| 类别 | 展示 | 数据政策 |
| --- | --- | --- |
| 可用 | 本次出口、延迟、元数据 | 默认进入“追加可用”候选 |
| 部分出口异常但可用 | 可用分类内的警告标记和原因 | 不改成 unknown，不伪造双栈 |
| 失效／最终超时 | 失败原因和结果 | 普通检测不自动入桶 |
| 未知 | 接口、错误码、原因和复检过程 | 可重试，不默认作为新增候选 |
| 未完成 | 剩余任务与续检入口 | 是任务状态，不新增节点状态枚举 |
| 格式无效 | 原始内容与修正提示 | 不进入自动入库候选 |

日志统一用 `components/probe-log.ts`、`probe-status.ts` 和现有工作台日志入口；保留失败主接口到备用恢复的诊断过程。不输出密钥或完整敏感响应。维护结果优先展示后端 `results[].lines`、`notificationMessage`、`message` 和 `completed`，不要只打印数量汇总或把计划当成实际解析结果。普通成功进度使用进度条，不逐地址刷日志。

## 5. 追加、删除和覆盖

### 5.1 默认追加可用结果

```text
当前草稿检测完成
→ 提取当前 revision 的 alive 结果
→ 明确目标池及 mode=append
→ 调用 previewPool
→ 展示服务端差异
→ 用户确认
→ 调用 savePool，显式传 mode 并请求回执
→ 按回执更新对应池视图
```

按钮名称必须说明动作：例如“预览追加可用”“确认追加到「池名」”。不能继续用含义不明的“入库”代替追加与覆盖。

- 默认仅使用当前检测报告的可用 `line`。
- 无可用项时明确说明原因，不假称写入成功。
- 不默认混入 unknown 或未完成项。
- 可保留“直接追加输入地址”作为明确的次级动作，不暗设必须先检测的门槛。该动作同样走预览、后端校验和确认。
- 追加不删除原池中没有出现在候选集的地址。
- **检测后追加不是洗库**：原池的失败地址不会因为本次只追加成功项就被清除。

### 5.2 管理视图删除

- 删除范围由当前池中的明确选择集表达，不再靠输入框列出的地址暗示。
- 使用规范化地址 key 维护选择集。
- 切池清空选择。筛选改变时，默认清空选择并提示，避免删除隐藏的旧选择；如保留跨筛选选择，必须明确显示隐藏选择数量。
- 预览与提交都用 `mode: remove`，只移除选择地址。
- 无选择不发起写入；不要把空选择解释成删除全部。
- 人工明确删除不自动入垃圾桶；入桶仍只由洗库／维护的既有入口处理。

### 5.3 完整编辑和覆盖

- 只有明确的完整编辑模式提供覆盖保存。
- 进入编辑时记录目标池和原文；切池或离开需确认未保存编辑。
- 预览与提交都用 `mode: replace`。
- 确认区显示目标池、前后地址数量、新增／更新／移除数量、未识别行及独立备注数量变化。
- 逐地址 `changes` 不是完整文本逐行 diff；覆盖替换整个文本，需要提示独立备注也可能改变。
- 空 replace 表示清空池内容，必须有独立的危险确认；不能由“清空输入”触发。
- 删除池容器与清空内容是不同动作。默认池、垃圾桶容器继续遵守现有删除限制。

## 6. 后端接口的准确使用

所有请求走 `app/web/src/api/client.ts`。

| 目的 | 客户端方法 | 说明 |
| --- | --- | --- |
| 列表／名称／顺序 | `pools()` | 使用服务端顺序，保留 `pool-options.ts` 的降级规则 |
| 读取完整池 | `readPool(key, signal)` | 查询可能陈旧，不代表刚写入确认 |
| 检测 | `checkBatch(...)` | 逐地址检查，不写库 |
| 预览 | `previewPool(key, content, mode, signal)` | POST `/api/pools/:key/preview`，只读 |
| 保存 | `savePool(key, content, mode, signal, true)` | PUT 同一池接口，请求回执 |
| 洗库 | `cleanPool(key, signal)` | 会写库与入桶，确认目标后调用 |
| 恢复 | `restoreTrash(addresses, options, signal)` | 后端决定来源回退和有序恢复 |
| 清空垃圾桶 | `clearTrash(signal)` | 独立危险确认 |

### 6.1 不依赖默认 mode

当前方法的默认值不同：

```ts
previewPool(key, content, mode = 'append', signal)
savePool(key, content, mode = 'replace', signal, returnReceipt = false)
```

新流程必须显式传递同一 mode，例如：

```ts
const mode = 'append' as const;
const preview = await client.previewPool(poolKey, candidateText, mode, signal);
// 展示预览，确认期间绑定 poolKey、candidateText、mode 和 draftRevision。
const result = await client.savePool(poolKey, candidateText, preview.mode, signal, true);
```

上例是调用契约示意，不是可以跳过确认和竞态保护的完整组件代码。

### 6.2 预览字段

```ts
interface PoolPreviewResponse {
  ok: true;
  poolKey: string;
  mode: 'append' | 'replace' | 'remove';
  currentCount: number;
  count: number;
  added: number;
  updated: number;
  removed: number;
  changed: boolean;
  unrecognized: { before: number; after: number };
  standaloneComments: { before: number; after: number };
  changes: Array<{
    address: string;
    kind: 'add' | 'update' | 'remove';
    before?: string;
    after?: string;
  }>;
}
```

展示规则：

- 预览的 added／updated／removed 是真实地址差异；不能拿旧覆盖响应的 added／replaced 计数代替。
- 有文本规范化或备注变化时，地址差异可能为零而 `changed: true`，必须解释，不能误报“完全无变化”。
- `changed: false` 时说明“本次读取快照无变化”，可以关闭预览，不假装完成了一次新写入。
- 不静默截断后端差异。大量条目可以在前端分页／折叠查看，完整数量仍可见。
- 预览不会重新检测，也不会给数据加锁。

## 7. 回执、陈旧读取和竞态

请求回执后，成功响应可包含：

```ts
receipt?: {
  poolKey: string;
  content: string;
  written: boolean;
}
```

### 7.1 成功且 `written: true`

- 核对回执 poolKey 与提交对象一致。
- 使用回执 content 显示**本次操作接受的内容**，使用结果 count 更新对应池的确认数量。
- 不再为了确认提交而立刻用一次 `readPool` 覆盖它。
- 已发出的旧读取／预览不能覆盖这次确认，复用请求序号保护。
- 写入后列表刷新也可能陈旧，不能把当前池的确认数量无提示地回退。
- 本次操作确认值不等于全球最新值，其他操作之后仍可能改变数据。

### 7.2 `written: false`

- 表示当前读取快照上的计划没有执行新 put。
- 不显示“已成功写入”，不把回执当作一次新提交凭据。
- 如无先前确认值，可以把它作为读取快照展示；不能据此覆盖另一份已确认结果或宣称全局没有变化。

### 7.3 后续读取与确认值不同

没有服务端版本 token 时，不能确定不同内容是陈旧读取，还是另一个操作的新修改。

- 文案说明“读取结果与本次确认值不同，可能尚未同步或已被其他操作修改”。
- 提供明确的“保留本次确认显示／采用读取快照”选择，或在显式刷新中说明将采用读取结果。
- 不无界轮询，不用固定 sleep 假装获得一致性，不自动覆盖未保存编辑。
- 不伪造 etag、事务锁或原子版本校验；需要强一致能力时另行设计后端。

### 7.4 写入失败和请求取消

- 保留草稿与操作目标，明确显示失败，不清空输入。
- 500／网络断开时不能断言服务端已回滚；只说明未取得成功确认。
- 一次明确重试复用同一份输入和 mode，不能因重复点击叠加多个提交。
- 不以 AbortSignal 取消客户端等待就假称撤销了已发出的写入。
- 提交中可禁用相关写操作并说明原因；若允许切池，旧操作完成只能更新它所属池，不能覆盖新池视图。
- 预览期间输入、目标池或候选集合变化，旧预览立即失效并提示重新预览。

## 8. 管理、筛选与垃圾桶的边界

### 8.1 筛选

- 使用 `domain/pool-filter.ts` 的已有语法和比较规则。
- 筛选只是视图查询，不改变原始输入或保存的数据。
- 需要生成写入候选时，提供独立、明确的“将当前结果用作操作对象”，再走预览。
- 无效端口、空条件或非法 OR 分支等错误不偷偷忽略；保持当前解析器的明确失败行为。
- 未知栈不匹配双栈。不得根据入口 IP 地址家族伪造出口栈。
- 不另写 country／ASN／stack 元数据合并和判定算法。

### 8.2 洗库

- 调用前说明目标池和有副作用，不把它放在“只读检测”按钮后面偷偷执行。
- 保持后端规则：有 unknown 或无法识别项时整池跳过；确定失效入桶完成后才移除来源。
- 服务端洗库单次最多 200 个不同有效地址；更大池明确说明限制，不静默只洗前 200 条。
- 本轮不实现新的分批写库策略、洗库预览会话或后台队列。
- 返回 skipped 时显示原因，保留当前池快照，不假称完成清理。

### 8.3 垃圾桶

- 正常追加／覆盖入口在该模式不可用，并明确说明原因。
- 来源显示复用 `domain/trash.ts` 的读取规则，组件不复制“来自”注释解析。
- 单次恢复上限为现有契约的 1,000 个地址；超出明确报错，不静默截断选择。
- 恢复让服务端处理原池缺失回退、补齐元数据和先写目标再清理来源。
- 操作失败不得清空本地选择或假称全部回滚；保留明确的重试入口。
- 清空垃圾桶独立确认，不与“清空输入”共用动作。

## 10. 视觉与可访问性

- 保持 DDNS Pro 现有风格，只调整 IP 库功能块。
- 高频动作“图标 + 文字”，次级和危险动作以文字为主。
- 结果表只展示当前场景需要的字段。没有本次检测结果的库条目显示“未检测”，不伪造历史状态或延迟。
- 窄屏优先保留地址、状态、选择和主要操作，次要元数据可以展开；不得把操作区挤出页面。
- 表格可内部横向滚动，页面不能横向溢出；文本不能覆盖按钮。
- 切换模式、结果过滤器有可访问名称和正确选中状态；表单标签关联，标题不跳级。
- 沿用现有 modal、feedback、icon 组件和语义变量，不写孤立尺寸或另一套样式。
- 实施后必须亲自查看桌面和窄屏实际截图。扫描通过不能代替视觉验收。
- 合并前按 `AGENTS.md` 进行独立复核：需求归属、视觉层级、留白密度、功能正确性都要覆盖。

## 11. 实施顺序

1. **核对最新基线**：读取 `AGENTS.md`、当前 `beta` 和接口类型，确认没有其他会话同时切同一工作目录。不要从旧快照回退最近 UI 改进。
2. **状态重构**：分清池快照、草稿、检测、编辑与预览；维持现有功能闭环，重构不夹带新行为。
3. **交互实现**：三个操作模式、结果分类、预览确认、显式 mode 和回执消费。
4. **异常与竞态验证**：加入切池、编辑失效、旧响应、KV 陈旧读取、无变化和失败重试测试。
5. **清理与验收**：删除替换后的旧分支、未使用导出／样式和重复实现，完成功能及视觉验收。

提交按实际性质分为 refactor／feat／fix，不把纯重构与功能混成无法回退的提交。程序代码或用户可见行为变更按仓库要求同步运行版本；纯文档和维护规则提交不更新运行版本。前端实施不要自动合并 `main` 或部署。

## 12. 必须覆盖的验收用例

| 场景 | 预期 |
| --- | --- |
| 单纯检测／切换结果分类 | 不写 KV、垃圾桶或 DNS |
| 检测完成 | 原始草稿保留，可用默认可见，未知和失败有入口 |
| 主接口失败、备用恢复 | 最终可用，日志仍显示主接口错误 |
| 一栈可用另一栈异常 | 可用分类内警告，不误判整节点或双栈 |
| 停止再续检 | 不重复请求已完成源行，进度与结果组正确 |
| 追加可用 | 原池无关条目保留，metadata／备注按后端规则合并 |
| 候选有无效内容 | 明确报错或提示修正，不静默剔除后覆盖 |
| 清空输入 | 零写入，不改变已存池 |
| 删除选择 | 仅选择地址移除，隐藏／旧选择不被误用 |
| 覆盖预览 | 前后数量、真实地址差异、未知行与独立备注影响可见 |
| 输入／mode／目标变化 | 旧预览失效，不提交旧候选 |
| 成功回执后旧读取返回 | 不无提示覆盖确认值 |
| 新读取与回执不同 | 不武断认定新旧，提供明确选择／说明 |
| written=false | 不假称执行了新的 put |
| 写入失败／超时等待中断 | 保留草稿，不假称服务端已回滚 |
| 切池时慢读取返回 | 不覆盖新池或导入草稿 |
| 洗库有未知／无效项 | 显示 skipped，原池不被当作已清理 |
| 大于 200 地址洗库 | 明确限制，不部分处理却称全量完成 |
| 垃圾桶恢复或清理失败 | 保留选择和错误，不隐藏部分完成事实 |
| 默认池／垃圾桶容器删除 | 保持既有拒绝规则 |
| 保存顺序、重命名／删除目标、晚到的绑定读取 | 保留最近 UI 的身份、顺序和状态保护，不按下标回退 |
| 375px 与桌面、长地址／长池名／错误文本 | 无页面溢出、遮挡、控件重叠，键盘可操作 |

至少执行：

```sh
cd app
npm run check
npm run audit:ui
npm run audit:ui:regression
npm run audit:flows
```

以及仓库根目录的 `git diff --check`、`git status --short`。

- 更新 UI 测试选择器时优先使用可访问名称或稳定动作标识，不机械依赖按钮第几个。
- 不通过删掉断言、隐藏错误、无界等待或放宽门禁来让测试通过。
- 类型／单元测试不能替代真实浏览器操作，无障碍扫描不能替代截图审阅。
