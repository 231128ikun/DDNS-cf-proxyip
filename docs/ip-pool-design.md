# IP 池与存储设计说明

本项目的目标只有一个：**让托管的 proxyip 域名始终能解析出可用的代理 IP**。
IP 池、垃圾桶、维护任务、通知都围绕这个目标服务，任何偏离这个目标的复杂度都不应该进入代码。

## 一、参考项目与可借鉴做法

| 项目 | 做法 | 我们采用的部分 |
| --- | --- | --- |
| [XIU2/CloudflareSpeedTest](https://github.com/XIU2/CloudflareSpeedTest) | 先测延迟、再测下载速度，按结果排序取最优；有明确阈值 | 维护补货改为“先探测一个有界窗口，再按结果挑最快”，不再按池顺序碰到谁算谁 |
| [badafans/better-cloudflare-ip](https://github.com/badafans/better-cloudflare-ip) | 按丢包/质量筛选，而不是只看一次连通性 | 只有可信探针明确判定失效才淘汰；未知一律保留（已有规则） |
| [cmliu/WorkerVless2sub](https://github.com/cmliu/WorkerVless2sub) | 上游列表用 URL 维护（`ADDAPI`），条目支持 `地址:端口#备注` 与最低质量阈值（`DLS`） | 远程加载、`# 备注`、出口国家/ASN/栈筛选（已有）；上游定时同步列入后续 |
| [cmliu/edgetunnel](https://github.com/cmliu/edgetunnel) | KV 存 proxyip 列表，提供增删接口与快速订阅入口 | 单池一个 KV value、写入统一走用例层（已有） |

结论：我们已有的能力（远程加载、去重、筛选、垃圾桶、一键洗库、批量检测、通知基线）方向是对的；
本轮按上表补上“有界探索 + 延迟择优”，并修掉了“全失效的池会一路探测到池底”的预算风险。

## 二、存储决策：KV 还是 D1

**结论：池本体继续用 KV；只有加入“每个 IP 的健康历史”时才引入 D1，且只把历史放进 D1。**

理由：

- 现在存的东西是**整块读、整块写**的配置型数据：`app_config`、`ip_pool_*`、`domain_pool_mapping`、`pool_stats_baseline`。
  KV 的读性能和成本都优于 D1，写入频率也很低（一次保存/洗库 = 一次写）。
- KV 的边界是明确的：**同一个 key 每秒只能写一次**、没有事务和条件写、不能按条目查询或部分更新。
  一旦出现“每轮维护要更新每个 IP 的一行状态”，KV 就会退化成“整块重写 + 写竞争”，这时候 D1 才划算。
- 端口层已经把存储隔离好了（`PoolRepository` / `PoolCatalog` / `MaintenanceSource` / `MaintenanceStats`），
  换存储只需要替换 adapter，领域规则和用例不动。

**引入 D1 的触发条件**（满足任意一条就该做）：

1. 需要保存每个 IP 的检测历史（最后检测时间、连续失败次数、最近延迟）；
2. 需要按条件查询池内条目（例如“最近 24 小时未检测的地址”）而不是整块读出来在内存里过滤；
3. 多个维护目标并发写同一份数据，KV 的“后写覆盖前写”开始丢数据；
4. 需要跨池统计。

**迁移形态**（如果触发）：池内容仍留在 KV（保持现有数据格式与回滚能力），
新增 D1 表 `ip_health(address, pool_key, checked_at, ok_count, fail_count, last_latency_ms)`，
只让维护流程按历史排序候选；KV 与 D1 之间没有第二份“池数据”，不产生两套事实来源。

## 三、后续优先级

1. **IP 健康历史（D1）**：维护时记录结果，补货按“健康分 + 延迟”排序，并对长时间未检测的地址做轮转，
   避免永远只探测池头的几十条。
2. **上游列表定时同步**：把远程 TXT/订阅地址存进配置，cron 里先同步再维护（参考 `ADDAPI` 模式）。
3. **结果导出**：批量检测结果支持复制/导出（参考 CloudflareSpeedTest 的输出习惯），便于离线核对。

不做的事：不引入服务端数据库之外的运行依赖，不复制第三方面板的远程代理模型，
不为“以后可能用到”的场景预留抽象。
